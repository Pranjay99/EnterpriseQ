💡 The Idea — What Enterprise Q Solves

In most organizations, valuable knowledge is scattered across CSV exports, Excel workbooks, JSON dumps, and PDF reports. Getting answers out of them requires either technical skills (SQL, pandas, BI tools) or waiting on an analyst. Enterprise Q removes that barrier: it is a unified natural-language interface over structured and unstructured enterprise data.

A user simply uploads a file and asks a question — "What is the average attrition rate per department?" or "Summarize the risks section of this contract". Behind the scenes, a set of specialized LLM agents figures out how to answer: generating and safely executing SQL, analyzing a DataFrame, retrieving relevant document passages (RAG), performing math, or synthesizing insight across up to 10 documents at once.

Problems it addresses

🔍 Data access bottleneck

Non-technical users can query tabular data without knowing SQL or pandas — the Text-to-SQL and DataFrame agents translate plain English into executable analysis.

📄 Buried document knowledge

PDFs are chunked, embedded, and stored in a vector database, so answers are grounded in the actual document content with cited sources (RAG) — not hallucinated.

🗂️ No document memory

A permanent Document Catalog auto-generates summaries, categories, and tags for every uploaded PDF, tracks usage stats, and lets you pin and revisit documents anytime.

🔀 Cross-document analysis

The Multi-Doc agent can synthesize, compare, or answer per-document across many files in one query — work that normally takes hours of manual reading.

📊 Insight, not just answers

Agents emit chart hints that are turned into interactive Plotly visualizations automatically — every numeric answer can come with a graph.

💸 Zero-cost operation

Built entirely on the Google Gemini free tier, with a zero-LLM-cost heuristic router and safe local tool execution (calculator, unit converter) to conserve API quota.

🏗️ Architecture

Enterprise Q is a classic three-tier application with an agentic middle layer: a Next.js frontend, a FastAPI backend that routes every request through the right agent, and a storage layer combining an in-memory session store, SQLite, and a persistent ChromaDB vector store. All intelligence is provided by Google Gemini 2.5 Flash via LangChain.

🔄 Data Flow

Flow 1 — File Upload & Ingestion

Every interaction starts with POST /api/upload/{session_id}. The pipeline branches on file type:

  1. The upload router validates the file type (.csv .xlsx .xls .json .pdf) and enforces the size cap (default 20 MB), then writes the file to a temp location.
  2. Tabular files (CSV / Excel / JSON) are parsed into a pandas DataFrame and stored in the in-memory session store; the DataFrame is also mirrored into a sandboxed in-memory SQLite database so the SQL Agent can query it.
  3. PDF files are split into text chunks by the PDF loader, embedded with gemini-embedding-001, and ingested into a session-scoped ChromaDB collection for immediate chat.
  4. PDFs are also ingested into a permanent ChromaDB collection, and Gemini auto-generates a summary, category, and tags which are saved to the SQLite catalog (catalog.db) — making the document searchable and reusable forever.

Flow 2 — Chat Query Routing

When a question arrives at POST /api/chat, the chat router decides which agent answers, in this priority order:

  1. Multiple doc_ids present? → route to the Multi-Doc Agent, which retrieves chunks from every selected catalog collection and answers in the requested mode (synthesize / compare / per-doc).
  2. Single doc_id present? → route to the RAG Agent against that document's permanent catalog collection, and update its query-count / last-accessed stats.
  3. Mode = general, or no data uploaded yet and the Orchestrator Agent classifies the question as MATH or REASON → route to the General Agent and its local tools.
  4. Documents uploaded in session (RAG mode / auto) → the RAG Agent retrieves the most similar chunks from the session's ChromaDB collection, injects them as context, and Gemini produces a grounded answer with cited sources.
  5. Tabular data with SQL mode (or auto) → the SQL Agent: Gemini sees the table schema, generates a query, the backend validates it is a single read-only SELECT/WITH statement (blocking INSERT/UPDATE/DROP/chaining), executes it against the in-memory SQLite DB, and Gemini summarizes the results.
  6. Otherwise → the Data Agent: a compact DataFrame summary (shape, columns, sample rows, descriptive stats) is injected into the prompt along with conversation memory, and Gemini analyzes it directly.
  7. Chart generation — if the agent's answer includes a chart hint like Chart: bar on Department vs AttritionRate, the chart generator builds an interactive Plotly figure (JSON) which the frontend renders inline.
  8. The response returns as { answer, chart_json, sql_query, sources } — so the user sees the answer, the evidence, and how it was derived.

🤖 The Agents

Six specialized agents live in backend/agents/. Each owns one style of reasoning; the chat router composes them into a single seamless experience.

🧭 Orchestrator Agent zero LLM cost

orchestrator_agent.py — Classifies incoming questions as MATH, REASON, or OTHER using pure keyword and regex heuristics (e.g. detecting numeric expressions like 12 * 34, or reasoning cues like "prove that", "syllogism"). Because it never calls the LLM, routing consumes no API quota — a deliberate design choice for the free tier.

📊 Data Agent DataFrame analysis

data_agent.py — Builds a token-efficient summary of the loaded DataFrame (shape, columns, first rows, descriptive statistics) and sends it to Gemini together with the question via a LangChain ConversationChain. Maintains per-session conversation memory so follow-up questions have context, and parses chart hints from the answer to trigger Plotly generation.

🗃️ SQL Agent Text-to-SQL

sql_agent.py — Five-step flow: (1) Gemini receives the table schema and question, (2) generates a SQL query, (3) the backend validates it is a single read-only SELECT/WITH — rejecting INSERT/UPDATE/DELETE/DROP/PRAGMA and statement chaining, (4) executes it against the sandboxed in-memory SQLite copy of the uploaded data, (5) Gemini summarizes the raw results into plain English. The generated SQL is returned to the user for full transparency.

📚 RAG Agent grounded document Q&A

rag_agent.py — Runs similarity search over ChromaDB (session collection or a permanent catalog collection), assembles the top-matching chunks into a context block, and asks Gemini to answer only from that context. Returns cited source filenames alongside the answer, so users can verify where information came from.

🔀 Multi-Doc Agent cross-document

multi_doc_agent.py — Retrieves relevant chunks from each selected document's collection (up to 10), annotates them by source, and answers in one of three modes: synthesize (one unified answer across all docs), compare (similarities and differences), or per_doc (a separate answer for each document).

🧮 General Agent tool-using agent

general_agent.py — A LangChain tool-calling agent with four tools:

ToolWhat it does
calculatorSafe math evaluation via an AST whitelist (no eval()) — supports sqrt, log, trig, powers.

Safety & cost design choices

🛡️ SQL sandboxing

LLM-generated SQL runs only against a per-session in-memory database, and only single read-only SELECT/WITH statements pass validation.

🛡️ Safe math

The calculator evaluates expressions through an AST operator whitelist — never eval().

🛡️ Upload guards

File type allowlist and configurable size cap before any processing happens; CORS restricted to configured origins.

💸 Quota-aware routing

The orchestrator classifies questions with regex/keywords instead of an LLM call, and compact DataFrame summaries keep token usage low.

Quick start

# 1. Configure environment
cp .env.example .env        # add your GOOGLE_API_KEY

# 2. Backend
cd backend
pip install -r ../requirements.txt
uvicorn main:app --reload    # → http://localhost:8000  (Swagger at /docs)

# 3. Frontend
cd frontend
npm install
npm run dev                  # → http://localhost:3000
